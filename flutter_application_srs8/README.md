## 🏛 Стек технологий и архитектура

Приложение построено по многослойной компонентной архитектуре с четким разделением ответственности:

```
┌────────────────────────────────────────────────────────┐
│                   Presentation Layer                   │
│        (Screens · Widgets · BLoC State Management)     │
└───────────────────────────▲────────────────────────────┘
                            │
┌───────────────────────────┴────────────────────────────┐
│                    Repository Layer                    │
│      (PostRepository: Кэш, преобразование, ошибки)     │
└─────────────▲────────────────────────────▲─────────────┘
              │                            │
┌─────────────┴───────────────┐ ┌──────────┴─────────────┐
│      Remote Data Source     │ │    Local Data Source   │
│ (Retrofit · DioClient · API)│ │ (PostCache: SharedPreferences) │
└─────────────▲───────────────┘ └────────────────────────┘
              │
┌─────────────┴───────────────┐
│  JSONPlaceholder REST API   │
└─────────────────────────────┘
```

- **UI / Presentation**: Flutter Material 3, `flutter_bloc` 9.x.
- **Repository**: координация источников данных, трансформация сетевых исключений в доменные `AppException`, кэширование первой страницы.
- **Remote Data Source**: `dio` 5.x, `retrofit` 4.x с автоматической кодогенерацией.
- **Local Data Source**: `shared_preferences` для надежного персистентного кэширования в формате JSON.
- **Serialization**: `json_serializable` и `json_annotation` для строгой типизации моделей без ручного парсинга.

## 💡 Обоснование ключевых компонентов

### 1. Зачем нужен `Dio`?
- **Гибкая конфигурация**: единый `BaseOptions` с базовым URL, таймаутами соединения (`connectTimeout`) и чтения (`receiveTimeout`).
- **Интерцепторы (Interceptors)**: возможность централизованно добавлять технические заголовки (`Accept`, `Content-Type`, `X-Client-App`, `X-Request-Timestamp`) и логировать запросы/ответы через `LogInterceptor`.
- **Единая обработка ошибок**: перехват сетевых таймаутов, отсутствия интернета (`SocketException`), ошибок 4xx и 5xx в одной точке (`ApiInterceptor`).
- **Синглтон `DioClient`**: предотвращает создание нового экземпляра HTTP-клиента и сокет-пула на каждый запрос.

### 2. Зачем нужен `Retrofit`?
- **Декларативное описание контрактов**: эндпоинты, HTTP-методы (`@GET`, `@POST`), query-параметры (`@Query`) и пути (`@Path`) объявляются в виде чистого интерфейса Dart.
- **Исключение человеческого фактора**: автоматическая генерация URL, сериализация параметров и десериализация ответа через генератор `retrofit_generator`.
- **Читаемость и тестируемость**: легкое мокирование через интерфейс `PostApi` в юнит-тестах.

### 3. Зачем нужен `json_serializable`?
- **Надежность и строгая типизация**: генерирует безопасный и оптимизированный код десериализации (`fromJson`) и сериализации (`toJson`).
- **Поддержка вложенных моделей**: автоматическая сериализация сложных иерархий (например, объект `User` содержит вложенные объекты `Company` и `Address`).
- **Защита от сбоев**: в моделях реализована дополнительная обертка для корректной обработки непредвиденных типов или отсутствующих полей без аварийного завершения приложения.

### 4. Зачем нужен `Repository` (`PostRepository`)?
- **Изоляция UI**: слой представления (`PostListBloc`, экраны) ничего не знает о `Dio`, `Retrofit` или `SharedPreferences`.
- **Управление источниками данных**: репозиторий решает, отдавать данные из кэша или с сервера, и обновляет кэш при успешных ответах.
- **Трансформация исключений**: сетевые ошибки `DioException` преобразуются в типизированные пользовательские сообщения `AppException`.

## 🌐 Сетевой слой и Retrofit API

В интерфейсе `PostApi` реализовано **7 запросов** (5 обязательных + 2 дополнительных):

| № | Метод | Endpoint | Назначение |
|---|---|---|---|
| 1 | `GET` | `/posts?_page={page}&_limit={limit}` | Получение списка постов с постраничной пагинацией |
| 2 | `GET` | `/posts/{id}` | Получение подробной информации о конкретном посте |
| 3 | `GET` | `/posts?userId={id}&_page={page}&_limit={limit}` | Фильтрация публикаций по идентификатору автора |
| 4 | `GET` | `/posts/{id}/comments` | Получение комментариев к выбранному посту |
| 5 | `POST` | `/posts` | Создание новой публикации на сервере |
| 6 | `GET` | `/users` | Получение списка авторов для выбора в фильтре и форме |
| 7 | `GET` | `/users/{id}` | Получение информации об авторе (включая компанию и адрес) |

## 💾 Локальное кэширование и офлайн-сценарии

Кэширование реализовано в классе `PostCache` с использованием `SharedPreferences`:
1. **Первый запуск приложения**:
   - Локальный кэш пуст.
   - Отображается полноэкранный индикатор загрузки (`LoadingIndicator`).
   - Выполняется запрос к серверу на получение первой страницы (10 постов).
   - После успешного ответа данные сохраняются в локальный кэш и отображаются пользователю.
2. **Повторный запуск приложения**:
   - Данные мгновенно считываются из кэша и выводятся на экран со статусом `PostListStatus.cached`.
   - В верхней части списка отображается баннер `«Отображаются кэшированные данные»`.
   - Параллельно в фоне отправляется запрос на сервер для актуализации данных.
   - При успешном ответе список обновляется свежими данными, кэш перезаписывается, а баннер кэша скрывается (`isCached = false`).
3. **Отсутствие интернета (офлайн-режим)**:
   - Если сервер недоступен или отсутствует соединение, ранее закэшированные посты **не удаляются** и остаются на экране.
   - Пользователь видит баннер `«Отображаются кэшированные данные. Сервер недоступен или идет фоновое обновление»`.
   - При попытке ручного обновления через pull-to-refresh показывается информативный SnackBar с сообщением об отсутствии соединения, а кэш сохраняется в целости.

## 🔍 Пагинация, поиск и фильтрация

1. **Пагинация (Задание C)**:
   - Загрузка порциями по 10 постов (`_limit=10`).
   - Автоматическая подгрузка при приближении к концу списка (`ScrollController` фиксирует остаток менее 250px).
   - **Защита от дублирования**: проверка флагов `isLoadingMore` и `hasReachedMax` предотвращает повторные параллельные вызовы одной страницы.
   - **Обработка ошибок**: при сетевом сбое при подгрузке следующей страницы внизу списка появляется сообщение и кнопка «Повторить попытку».
2. **Поиск и фильтрация (Задание D)**:
   - **Поиск по заголовку**: реализован локально по загруженным данным с явным бейджем в UI: *«Поиск выполняется среди загруженных постов»*.
   - **Фильтрация по автору**: выбор автора из выпадающего списка / модального окна (сброс старых страниц, пагинация для выбранного автора без смешивания данных).
   - **Сортировка по ID**: кнопка переключения направления сортировки (по возрастанию / убыванию) с анимированной стрелкой.
   - **Сброс**: кнопка «Сбросить» возвращает ленту к полному серверному каталогу.

## ✍️ Создание поста и валидация (Задание F)

- Отправку `POST` через Retrofit.
- Отображение диалогового окна с подтверждением и полученным сервером объектом.
- Добавление поста в начало ленты с пометкой `«создан локально»` (зеленый бейдж).
